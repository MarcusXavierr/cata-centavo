# Phase 0.5 reconnaissance against the live Pluggy API

Captured 2026-07-26, read-only, against the author's own wallet: three connections on connector 200 (MeuPluggy), six accounts (three checking, three credit cards), 1751 transactions, 26 bills, 130 categories. Every figure below was recomputed from the raw response bodies rather than taken from a summary. Amounts, descriptions, account numbers, names and UUIDs are excluded on purpose — the repository is public and the source is real statements.

**This is one wallet.** Where a finding differs between accounts, that is a sample of two or three, not a rule about Brazilian banking. The places where the sample size actually changes the conclusion are called out where they appear.

The headline is that the transaction endpoint the ADR is written against no longer exists, and that this account is currently returning the enrichment fields §12 was designed to live without. Both change what Phase 1 and Phase 2 have to build; only the first is unconditional.

## `GET /transactions` is gone

All six accounts, identical body:

```json
{ "message": "This endpoint is deprecated. Use GET /v2/transactions with cursor pagination instead.",
  "code": 410, "codeDescription": "ENDPOINT_DEPRECATED", "errorId": "<uuid>" }
```

410, not 404 and not a deprecation header on a working response. There is no fallback: the endpoint every `curl` line in §15 Phase 0.5 and every pagination sentence in §14.2 is written against returns nothing but this envelope. It does, at least, fail loudly and carry a `codeDescription`, which the `PATCH /items` refusal recorded in `pluggy-item-update.md` does not.

## The v2 contract, and what replaces §14.2's pagination rule

The envelope is two keys and nothing else:

```json
{ "results": [ … ], "next": "?accountId=<uuid>&after=<cursor>" }
```

No `total`, no `totalPages`, no `page`. Every offset-shaped parameter is rejected outright, and the rejection names the parameter:

| Query | Status | `message` |
|---|---|---|
| `?accountId=…&pageSize=500` | 400 | `property pageSize should not exist` |
| `?accountId=…&limit=500` | 400 | `property limit should not exist` |
| `?accountId=…&page=2` | 400 | `property page should not exist` |
| `?accountId=…&pageSize=10&page=1` | 400 | `property pageSize should not exist, property page should not exist` |
| `?accountId=…&perPage=100` | 400 | `property perPage should not exist` |
| `?accountId=…&first=10` | 400 | `property first should not exist` |
| `?accountId=…&from=2026-07-01` | 400 | `property from should not exist` |
| `?accountId=…&to=2026-07-26` | 400 | `property to should not exist` |
| `?accountId=…&itemId=x` | 400 | `property itemId should not exist` |
| `/v2/transactions` (no filter) | 400 | `accountId should not be null or undefined,accountId must be a UUID` |

So `accountId` is required, it is the only parameter accepted alongside `after`, and **there is no server-side date filter** — the `startDate` / `endDate` of `getTransactions` (§14.2) has to be applied by us, after fetching, or served from the cache. The endpoint validates by allowlist and refuses anything outside it, which at least means a wrong guess errors instead of being ignored.

The server picks the page size. Observed: 500 on a full page, 53 on the tail of the 1053-row account, 3 on an account holding 3. `next` is `null` on the last page, on every account, including the single-page ones. Rows come back **date-descending** on all six accounts, and the cursor is consistent with that — `after` base64-decodes to `<ISO-8601 timestamp>|<uuid>`, a keyset cursor over `(date, id)` rather than an opaque offset.

**`next` is a relative query string, not a URL.** It begins with `?`, carries no host and no path. The correct join is `${BASE}/v2/transactions${next}`.

§14.2's rule does not survive this verbatim:

> `pageSize = 500` (the documented maximum) on every paginated endpoint … Loop until `page >= totalPages`. **Terminate on the reported total, not on a short page**, and assert the invariant so a Pluggy change surfaces as an error rather than as missing money.

There is no total to assert against and no page size to send. What replaces it, for `/v2/transactions` only:

- **Terminate on `next === null`, and on nothing else.** A short page is now normal and carries no information — the 53-row tail and the 3-row single page are indistinguishable in shape.
- **Cap the hop count** and fail loudly on the cap, because "loop until the server says stop" has no natural bound if the cursor ever fails to advance.
- **Assert the cursor advances.** The invariant §14.2 wanted is still available, just relocated: if two consecutive responses carry the same `after`, or a page returns rows already seen, stop and error. That is the check that would have caught the bug below.
- The old rule still applies unchanged to `/accounts`, `/bills` and `/categories`, which are still offset-paginated and still return `{total, totalPages, page, results}`.

**The §14.2 failure mode was reproduced by accident during this very capture.** The first pass of the fetch script joined `next` as if it were a path, requested something that was not the next page, and stopped — with 500 rows from an account that holds 1053, no error, and a plausible-looking result. Exactly "nothing errors, aggregates are simply computed over a fraction of the data", on the first hour of contact with the new endpoint. The fixed script's comment is the scar: `// `next` is a relative query string ("?accountId=…&after=…"), not a URL.`

## Enrichment is arriving on this account — which is not the same as the ADR being wrong

§12.1 asserts that on the free tier `transaction.category` / `categoryId` "comes back `null` — useless", and the whole of §12 is built on filling that gap. On 2026-07-26, against this account, that is not what comes back.

| Field | Non-null | Rate |
|---|---:|---|
| `category` | 1745 / 1751 | 99.7% |
| `categoryId` | 1745 / 1751 | 99.7% |
| `merchant` | 393 / 1751 | 22.4% |
| `merchant.cnpj` (where `merchant` present) | 393 / 393 | 100% |
| `descriptionRaw` | 1693 / 1751 | 96.7% |
| `description` | 1751 / 1751 | 100% |
| `providerCode`, `providerId` | 0 / 1751 | always null |

By account type: 478/481 BANK (99.4%) and 1267/1270 CREDIT (99.8%). `category` and `categoryId` agree perfectly — zero rows where one is set and the other is not — and `category` is always exactly the `description` of the matching `/categories` entry, never the `descriptionTranslated`. The six uncategorized rows are three checking-account rows with no `descriptionRaw`, no `paymentData` and no `merchant`, and three card rows carrying MCC 9994.

**This does not refute §12.1, because this capture is not from the free tier.** The account is very likely on a trial or paid plan at the moment of capture, and the expectation is that `category`, `categoryId` and `merchant` stop arriving once it settles onto the free plan — which is what the spec's §1 table predicted all along ("Categorização automática: ❌ `category` vem `null`"). The honest statement of what was measured is: **the free-tier claim was not tested, because there was nothing free-tier to test it against.** What these numbers describe is the shape of a tier that includes enrichment.

So §12 is **dormant, not dead**. The override → counterparty → MCC derivation is the contingency for the day enrichment disappears, and the machinery it specifies is the thing that keeps the product working across that transition rather than surplus to it. Two consequences worth stating plainly:

- The closed N-category taxonomy (§12.4) has an obvious candidate now, and it is tier-independent: `/categories` is a public reference endpoint, it does not depend on the transaction enrichment, and adopting its ids means our categories and Pluggy's line up on any tier. See the taxonomy section below.
- Nothing here changes the design of `setCategory`, `setCounterpartyCategory` or the MCC table. It does change their *urgency*: while enrichment is arriving they are a correction layer over a mostly-correct default, and if it stops they become the only source.

**The §12.1 asymmetry is confirmed, and it decides what happens if enrichment goes away.**

| Signal | On CREDIT | On BANK |
|---|---|---|
| `creditCardMetadata.payeeMCC` | 1126 / 1270 (88.7%), 87 distinct codes | 0 / 481 |
| `paymentData.receiver.documentNumber` | 0 / 1270 | 366 / 481 (76.1%) |
| neither | 144 / 1270 | 115 / 481 |

The two halves of the wallet lose categorization in different ways. Cards keep MCC on nearly nine rows in ten and have no counterparty document at all. Checking accounts keep the counterparty document on three quarters of rows and have no MCC at all. Neither signal covers the other's half, which is precisely why §12.2 puts `setCounterpartyCategory` in V1 rather than deferring it with rules. About 15% of the wallet — 259 rows — would fall through to description text alone, which is the gap V2's rule engine exists to close.

One field that would be new information for §12: `merchant.cnpj` is populated on **every** row where `merchant` is present, cards included (267 CREDIT, 88 BANK). §12.1 lists `merchant.cnpj` as the field "exactly what Pluggy charges for", and on this tier a card purchase can carry a CNPJ. If that survives the tier change it would make counterparty matching work on cards too; the safe assumption is that it does not.

## Step 3 — the open-bill signal, and both candidate answers were wrong

§14.3 asserted the `PENDING` / `POSTED` split; the prior Go implementation tested `creditCardMetadata.billId == ""`. Cross-tabulated over 1270 card transactions:

| `status` | `billId` set | `billId` key absent |
|---|---:|---:|
| `POSTED` | 1196 | 0 |
| `PENDING` | 2 | 72 |

Distinct `status` values: `PENDING` and `POSTED` on cards, `POSTED` only on checking accounts.

- **`billId` is never an empty string.** When it is absent, the key is *omitted from the object entirely* — not `null`, not `""`. The prior implementation's `billId == ""` test would have matched zero rows out of 1270, silently reporting an empty open bill on every card.
- **The `PENDING` / `POSTED` split has real exceptions.** `POSTED ⇒ billId set` holds without exception (1196/1196), but the converse does not: two `PENDING` rows carry a `billId`, and both of those ids resolve to real bills returned by `/bills`. Both are on card A, the partial connection with three transactions total — a sample too small to say whether this is an institution quirk or a state a fuller card also passes through.
- **The two signals agree on 1268 of 1270 rows and disagree on 2.** Either one alone is right 99.8% of the time on this wallet, which is exactly the confidence profile that makes a wrong choice survive testing and fail in production.

The practical form: `status === "PENDING"` and a missing `billId` both mean "not yet on a closed bill", and where they disagree the `billId` is the stronger claim, because it names a bill that exists. Treating `billId != null` as "belongs to bill X" and `status === "POSTED"` as corroboration, rather than either as the primary key, is what the data supports.

**Every credit transaction carries `creditCardMetadata`** — 1270 of 1270, zero exceptions — and no checking-account transaction does (0 of 481). §14.3's warning not to exclude rows lacking `creditCardMetadata` costs nothing to honour here, because on this wallet there are none to exclude. The fee and credit rows the warning is about are present and *do* carry the object: `feeType` on 225 rows (`ANNUAL_FEE` 12, `OTHER` 213) and `otherCreditsType` on 213 (`OTHER` 213). They simply arrive with `billId` and without `payeeMCC`.

The `billId` ↔ `/bills` join is clean in both directions: 26 bills fetched, 26 distinct `billId` values on transactions, zero transaction `billId`s missing from `/bills`, zero bills never referenced.

| | With `paymentData` | Rate |
|---|---:|---|
| BANK | 426 / 481 | 88.6% |
| CREDIT | 10 / 1270 | 0.8% |
| overall | 436 / 1751 | 24.9% |

§12.1 predicted the asymmetry and the numbers are more extreme than the prose implies — on cards `paymentData` is not "usually absent", it is absent on 99.2% of rows.

Shape of the counterparty, over all 1751:

| Shape | Rows |
|---|---:|
| `paymentData` explicitly `null` | 1315 |
| `receiver` explicitly `null` | 70 |
| `receiver.documentNumber` set, `type: "CPF"` | 278 |
| `receiver.documentNumber` set, `type: "CNPJ"` | 88 |
| `{type: "", value: ""}` | **0** |

**§12.2's fear did not materialise at the wire.** There is no empty-stringed document object anywhere in 1751 transactions. When the counterparty is unknown, `paymentData.receiver` is explicitly `null` and the `documentNumber` key does not exist below it; when `receiver` is present, `documentNumber` is present too, on all 366. The `{type: "", value: ""}` collapse §12.2 warns about was a property of the prior implementation's value types, not of Pluggy's payload. **The `NULL`-not-`''` requirement stands unchanged** — it is now a rule about our own deserialization discipline rather than a defence against the API.

Digit-length histogram of `documentNumber.value`: 11 digits on 278 (CPF), 14 on 88 (CNPJ). Type and length agree on every row. **All 366 values carry punctuation** in Brazilian formatting, so §12.6's "digits only, punctuation stripped on write" is not optional — a raw value used as a join key would never match a user-supplied one.

`paymentData` sub-fields, over the 436 rows that have it: `paymentMethod` 436/436 (`PIX` 285, `OTHER` 125, `TEF` 12, `DEBIT` 10, `BOLETO` 4), `payer` 382/436, `receiver` 366/436, and `reason`, `receiverReferenceId`, `authenticationCode`, `referenceNumber`, `boletoMetadata` **null on all 436**. Within `receiver`: `documentNumber` 366/366, `routingNumberISPB` 221, `accountNumber` 220, `branchNumber` 220, `routingNumber` 197, `name` 102.

## Absence is signalled two different ways depending on nesting depth

Not on the checklist, but it decides how `pluggy/wire.ts` is written.

- **Top-level transaction fields are always present and explicitly `null`.** All 23 keys appear on all 1751 rows. `category: null` on 6, `merchant: null` on 1358, `paymentData: null` on 1315, `balance: null` on 1696, `providerCode: null` on 1751. No key is ever omitted, and no value is ever `""`.
- **Nested object fields are omitted entirely.** Inside `creditCardMetadata`, absence is a missing key on every field checked, with zero explicit nulls: `billId` absent on 72, `installmentNumber` and `totalInstallments` absent on 1148, `purchaseDate` absent on 1150, `payeeMCC` absent on 144, `cardNumber` and `billForecastDate` absent on 13, `feeType` absent on 1045, `otherCreditsType` absent on 1057. Same at the next level down — `paymentData.receiver` is explicitly `null`, but `receiver.documentNumber` is either present or the key does not exist.

So the Zod schemas need `.nullable()` at the top level and `.optional()` on nested members, and the two are not interchangeable. This is also why `exactOptionalPropertyTypes` earns its place: the distinction is real in the payload.

## Step 6 — instalment posting varies between two cards in the same wallet

§14.2 says posting behaviour varies by institution and warns against generalizing from a single bank. It varies between two cards belonging to the same person.

Grouping instalment rows by `description | totalInstallments | purchaseDate`:

| Card | Instalment rows | Distinct purchases | Purchases with >1 instalment posted | Largest group |
|---|---:|---:|---:|---:|
| card A | 2 | 1 | 1 | 2 |
| card B | 102 | 56 | **37** | 5 |
| card C | 18 | 18 | **0** | 1 |

Card C posts strictly one instalment per bill, 18 times out of 18. Card B posts several at once on two thirds of its instalment purchases, up to five rows for a single purchase. `totalInstallments` values observed: 2, 3, 5, 10, 12; `installmentNumber` ranges 1–12.

This is §14.2's pitfall confirmed inside one wallet, and it is the precondition for §14.3's warning: deducting `amount × (totalInstallments − installmentNumber)` per row on card B over-counts, because the rows it is deducting from are already present. Nothing in this wallet reaches the full 45×-instead-of-9× case — the largest simultaneous posting is five rows — but the direction of the error is confirmed and the guard is needed.

**§14.2's grouping recipe references a field that does not exist.** It says group by `description|totalAmount|totalInstallments` and lists `totalAmount` among the card metadata. `creditCardMetadata` carries no `totalAmount` key on any of 1270 rows. Its members are: `billId`, `installmentNumber`, `totalInstallments`, `cardNumber`, `payeeMCC`, `billForecastDate`, `purchaseDate`, `feeType`, `feeTypeAdditionalInfo`, `otherCreditsType`, `otherCreditsAdditionalInfo`.

`purchaseDate` is the replacement, and it is a better key than `totalAmount` would have been. It is present on 120 of the 122 instalment rows (absent only on card A's two). Substituting the row's own `amount` for the missing `totalAmount` merges distinct purchases: on card B it produces 55 groups instead of 56, and invents one group of twelve rows out of two unrelated purchases that share a description, an amount and an instalment count. That single fabricated group would then be read as "a 12× purchase posted all at once".

## The category taxonomy

`GET /categories` returns `{total: 130, totalPages: 1, page: 1, results: […]}` — offset-paginated like the other v1 endpoints, one page. Each entry is `{id, description, descriptionTranslated, parentId, parentDescription}`, with `descriptionTranslated` populated on all 130 (Brazilian Portuguese). 22 top-level entries, 25 entries have at least one child, 105 are leaves.

Four structural facts, all of which decide how the tree can be handled:

1. **It is three levels deep in places.** 22 entries at depth 1, 81 at depth 2, 27 at depth 3 — under Transfers, Services (Telecommunications, Education, Wellness and fitness, Tickets), Housing → Utilities and Transportation → Automotive. Any code assuming two levels loses the leaves.
2. **Parents are used as categories alongside their own children.** 18 non-leaf categories appear as a transaction's `categoryId` in this wallet, several of them heavily: Transfers 143 rows direct against 111 across its ten children, Services 101 direct against 24, Digital services 73 direct against 5, Shopping 62 direct against 96. So a group-by on `categoryId` scatters one concept across a parent and its descendants, and any aggregate has to roll descendants up into the parent or report a Services total that excludes most of what the user calls services.
3. **The id width is not fixed.** 126 ids are 8 characters; the four Insurance children (`200100000` … `200400000`) are 9, while their parent `20000000` is 8. Positional parsing breaks there, and so does substring parent-derivation: a rule of "first four characters, zero-padded" would produce `20010000`, which is not a category.
4. **Every `categoryId` observed in the data exists in `/categories`.** 56 distinct ids used, zero orphans. Validating an incoming `categoryId` against the fetched list is safe, and so is treating the list as the closed set §12.4 needs.

**Three entries contradict themselves.** `02030001` Real estate financing, `02030002` Vehicle financing and `02030003` Student loan each carry `parentId: "02000000"` (Loans and financing) but `parentDescription: "Financing"`, which is the description of `02030000`. The id pattern agrees with `parentDescription` and the `parentId` field does not. Build the tree from `parentId` and these three sit as siblings of Financing; build it from `parentDescription` or from the id prefix and they nest under it. `parentDescription` matches the referenced parent's `description` on the other 105 entries. This is the only place a naive four-character-prefix rule guesses a real but wrong parent, and it is also the reason not to derive the tree from ids at all — use `parentId`, and accept that these three are misfiled at the source.

## The sign convention inverts between BANK and CREDIT

Not on the checklist, and the sharpest edge found in this capture.

| Account type | `type: DEBIT` | `type: CREDIT` |
|---|---|---|
| BANK | 305 rows, `amount` **negative** | 176 rows, `amount` **positive** |
| CREDIT | 1210 rows, `amount` **positive** | 60 rows, `amount` **negative** |

Zero rows have `amount === 0`, and the mapping holds without exception on all 1751.

On a checking account, money leaving is negative. On a credit card, a purchase — money that will leave — is **positive**, and a payment or refund is negative. So `SUM(amount)` over a mixed set is not merely meaningless in the §14.1 sense of adding available cash to card debt; the two halves have opposite signs for the same economic direction, and a mixed sum partially cancels. "You spent R$ X this month" computed across a checking account and a card produces a number smaller than either, with no error anywhere.

This subsumes §14.1's pitfall #1 and is worse than it: pitfall #1 is about a total that is meaningless, this is about a total that looks plausible. The normalization belongs in `pluggy/mapper.ts`, at the point where a Pluggy transaction becomes ours, and `type` (`DEBIT` / `CREDIT`) is the field that makes it decidable — it is present and non-null on all 1751 rows.

## Multi-currency, and the field that solves it

| `currencyCode` | Rows | Where |
|---|---:|---|
| `BRL` | 1718 | all six accounts |
| `USD` | 32 | cards B and C |
| `CLP` | 1 | card B |

All 33 foreign rows are ordinary international card purchases, not a data fault. All six accounts declare `currencyCode: "BRL"` at the account level, so `transaction.currencyCode` differs from its account's on those 33 rows.

**`amountInAccountCurrency` is non-null on exactly those 33 rows and null on all 1718 BRL rows.** Pluggy supplies the converted figure precisely where `amount` is not in the account's currency, which makes the correct rule a one-liner — `amountInAccountCurrency ?? amount` — and makes naively summing `amount` a silent error of the §14.1 class, since 33 rows in a foreign unit disappear into a BRL total without any signal.

The author has scoped currency conversion out of V1. That decision is compatible with the above: nothing needs converting, because the conversion has already been done. What stays open is the presentation question — whether `getTransactions` reports the original amount and currency alongside the converted one — and whether `amountInAccountCurrency` can be relied on when the account's own currency is not BRL, which this wallet cannot answer.

## Smaller confirmations

- **`creditData.balanceCloseDate` is `null` on all three cards.** Pitfall #6 confirmed: `manageClosingDate` (§14.3) is not a defensive nicety, it is the only source of a closing day on this connector. `balanceDueDate` *is* populated on all three, as are `creditLimit` and `availableCreditLimit`. `creditData.level` and `creditData.status` are null on card A and populated on B and C.
- **`/bills` returns a non-empty list on all three cards** — 2, 12 and 12. §14.3 keeps its position that an empty list is a legitimate normal case, but on this connector it is not the observed case. `billClosingDate` is populated on all 24 bills of cards B and C and `null` on both of card A's, so the closing date is available per-bill even though it is missing from the account.
- **`amount` is a JSON number** on all 1751 rows, and no value has sub-cent noise — every one is exactly representable in whole cents. That is not a licence to keep it in a `number`: the risk is accumulation, not parsing, and the CLAUDE.md rule stands. It does mean the conversion to integer cents is lossless on real data.
- **Five transactions are dated after the capture instant**, all on cards (four on card C, one on card A), the furthest 2026-11-25 — four months ahead. These are instalments posted forward onto future bills. Any "this month" or "last 30 days" aggregate has to decide explicitly whether to include them, and a naive `date <= now` filter silently drops a card's future instalment schedule.
- **All 1751 transaction ids are distinct and UUIDv4-shaped.** That is a precondition for step 1, not an answer to it.
- **`date` carries a time component** and it is not uniform — most rows are `T03:00:00.000Z` (midnight BRT rendered as UTC), some carry a real timestamp. Comparing dates as strings works; comparing them as calendar days requires deciding a timezone, and UTC is the wrong one for a Brazilian midnight.
- **`balance` (the running account balance on a transaction) is populated on 55 rows out of 1751** — one checking account, none of the others, none of the cards. Not usable as a general field.
- **`operationType` is populated on 426 rows, all of them BANK** (`PIX` 281, `RESGATE_APLIC_FINANCEIRA` 33, `ENCARGOS_JUROS_CHEQUE_ESPECIAL` 25, `RENDIMENTO_APLIC_FINANCEIRA` 21, `OUTROS` 20, `CARTAO` 16, `FOLHA_PAGAMENTO` 12, `TRANSFERENCIA_MESMA_INSTITUICAO` 12, `BOLETO` 4, `CONVENIO_ARRECADACAO` 2). Portuguese-language enum, undocumented membership, zero coverage on cards.

`nextAutoSyncAt` on B and C is `lastUpdatedAt` plus exactly 24 hours, to the millisecond. That is the 24h auto-sync cadence the docs attribute to production applications, running on this tier, on this connector.

**`pluggy-item-update.md` needs correcting.** It records, under "What Connector 200 actually is":

> **No on-demand refresh, and no auto-sync visible either.** `nextAutoSyncAt: null` on an item whose `lastUpdatedAt` was two days old.

That observation was made against one item — the one this document calls connection A — and generalized. Two of three items carry a `nextAutoSyncAt`, so **auto-sync does run on connector 200 for some items**, and `nextAutoSyncAt: null` is a property of a particular item's state rather than of the tier or the connector. The rest of that section stands: the refusal of `PATCH /items/{id}` is unchanged, `item.connector.name` is still `"MeuPluggy"` and never the institution, and the lookback and quota tables still describe the layer beneath us.

What stays unknown is why A is stalled and what would restart it. Three days without a sync, no `nextAutoSyncAt`, no `autoSyncDisabledAt`, no error, no `statusDetail`, and the only `PATCH` we could send is refused by the connector. Nothing in the item payload distinguishes "not scheduled" from "will never be scheduled". The one correlate available: A is also the connection whose consent has `openFinancePermissionsGranted: null` where B and C list five permissions, and A is the connection with the thinnest data (three card transactions, two bills, six months of checking history against a full year on the others). One item, so this is a hypothesis, not a finding — a partially-established connection may be what a `null` `nextAutoSyncAt` means. And what moves `lastUpdatedAt` on a connector-200 item, the open question from the earlier document, is still open.

## `GET /consents?itemId=` returns a consent belonging to a different item

Also not on the checklist. On all three connections, `GET /consents?itemId={id}` returns exactly one consent whose own `itemId` field is a **different UUID** from the one queried — a different one for each of the three, none of them matching any of our configured ids.

The reading consistent with the connector's nature (`pluggy-item-update.md` §"What Connector 200 actually is": MeuPluggy is Pluggy's own aggregator, and the real Open Finance connection lives one level down) is that the consent belongs to the underlying item inside MeuPluggy, and the filter resolves through the layer while the returned object reports the inner id. It is not a stale or unrelated consent: each one's `createdAt` sits within about a minute of the corresponding item's `lastUpdatedAt`.

The consequence is narrow but real. `listSources` (§14.5) mitigates pitfall #7 via `fetchConsents`, and the consent's own `itemId` **cannot be used as the join key back to our connection** — the only reliable association is "this is what the endpoint returned when asked about that item". Correlating a list of consents back to a list of items would silently produce zero matches.

Consent fields, uniform across all three: `products` lists nine, `expiresAt: null`, `revokedAt: null`. Neither expiry nor revocation is exercised by this capture, so the shape of a revoked consent — the thing pitfall #7 is about — is still unobserved.

## Still open after this run

- **Step 1 — transaction id stability across a re-sync. Not answered, and it now costs more to answer.** §12's whole override design is keyed on `transaction_id`, and the plan was to fetch, `manualUpdate`, and diff. `PATCH /items/{id}` is refused by connector 200, so the forced sync is unavailable from the API. Answering it now requires a **manual refresh inside meu.pluggy.ai between two captures** — capture a range, refresh by hand in the web app, capture again, diff the ids. That is a human-in-the-loop procedure, and until it is run, `category_overrides` keyed on `transaction_id` rests on an assumption. The ids being UUIDv4 (rather than a hash of content) is weak evidence in both directions: server-generated ids can be stable or can be re-issued on re-fetch, and the shape does not say which.
- **Step 4 — is the general rate limit 360 per minute or per hour. Not answered.** Nothing was measured against it: the capture paced itself at 200ms between requests and issued 20 calls in the first script, so it never came close to either bound. No `RateLimit-*` or `Retry-After` header appears on any successful response, so the limit is not self-describing and a 429 has to be provoked to read it. The 20/min figure for `PATCH /items` remains documented and unconfirmed here, since no `PATCH` succeeded.
- **Which enrichment fields disappear on the free tier, and when this account transitions.** Unanswerable from these captures. The 99.7% `category` rate above describes a tier that includes enrichment; it says nothing about what the free tier returns, because this account is not on it. Needs Pluggy's own documentation or a question on their Discord: which of `category`, `categoryId`, `merchant` and `merchant.cnpj` are gated, and whether `creditCardMetadata.payeeMCC` and `paymentData` — which come from the card network and the payment rails rather than from Pluggy's enrichment — are gated with them. If MCC and `paymentData` survive and only `category` goes, §12's three-lookup design is exactly the right contingency and needs no change.
- **Whether the two `PENDING` rows carrying a `billId` are an institution quirk or a transient state.** Both are on the three-transaction card. A second capture of a fuller card across a bill closing would settle it.
- **The shape of a revoked or expired consent.** All three consents have `revokedAt: null` and `expiresAt: null`, so pitfall #7's actual payload is still unobserved.
- **Whether `amountInAccountCurrency` behaves the same on a non-BRL account.** No such account exists in this wallet.
